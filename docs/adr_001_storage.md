# ADR-001 — 저장소로 SQLite 를 쓴다 (PostgreSQL 로 가는 조건과 함께)

- 상태: **채택**
- 날짜: 2026-09-09
- 배경: 9/3 DB 멘토링에서 "요즘은 PostgreSQL 을 써야 하지 않느냐" 는 지적을 받았다.

## 결정

**Chat Shield 는 SQLite 를 쓴다.** 단, 지적의 실질(동시성)은 재보고 코드로 막았다.
PostgreSQL 이행 스키마(`src/joker/store/schema_postgres.sql`)를 저장소에 함께 둔다.

## 왜 SQLite 인가

1. **동시 쓰기가 구조적으로 없다.** 진단은 인프로세스 잡 큐의 단일 워커(`max_workers=1`)가
   직렬로 처리한다. 로컬 8GB 환경에서 LLM 동시 호출이 불가능해 내린 결정이라(0831),
   DB 계층에서 다중 쓰기를 감당할 이유 자체가 생기지 않는다.
2. **배포하지 않는다.** 진단 대상 모델(`qwen2.5:3b-instruct`)이 로컬 Ollama 에 있고,
   temperature 0 · seed 42 고정이 Before/After 비교의 전제다. 공용 서버에 얹으면 그 통제가 사라진다.
   서버가 없으므로 DB 서버도 없다.
3. **`git clone` 하면 그냥 돈다.** 팀원 5명 PC + 학원 PC 어디서든 설치·계정·포트 설정이 없다.
   회귀 테스트 7개 파일이 `tmp_path` 에 파일 DB 를 만들어 서로 격리되는 구조도 이것 덕분이다.
4. 데이터 규모가 작다 — 현재 `joker.db` 8.1MB / `tb_attempt` 10,619행.

## 지적의 실질은 동시성이었고, 실제로 구멍이 있었다

기존 코드는 `PRAGMA foreign_keys` 만 켜고 **저널 모드는 SQLite 기본값(`delete`)** 이었다.
이 모드는 **쓰기 트랜잭션이 열려 있는 동안 읽기가 대기한다.** 우리 구조가 정확히 그 모양이다 —
진단 워커가 `save_run` 으로 1행 + 공격 시도 114행을 한 트랜잭션에 쓰는 동안,
화면은 3초마다 `GET /api/runs` 로 같은 DB 를 읽는다.

`journal_mode = WAL` 로 바꾸고 실측했다(`scripts/db_concurrency.py --runs 400`).
쓰기: 진단 400회 연속 저장 · 읽기: `list_runs` 질의를 5ms 간격 반복 — **경합을 일부러 최대로 만든 조건**이다.

**★ 측정 환경을 반드시 같이 읽어야 한다.** 이 프로젝트는 진단 행마다 `env_profile` 을 저장한다.
환경 없는 숫자는 근거가 아니라는 원칙이고, 벤치마크도 예외가 아니다.
저장장치 속도에 따라 같은 코드가 수십 배 차이 난다.

### 측정 ① Linux aarch64 VM · SQLite 3.37.2 (느린 저장장치)

| 저널 모드 | 쓰기 시간 | 읽기 평균 | p95 | **최대** | 잠금 오류 |
|---|---|---|---|---|---|
| `delete` (기존 기본값) | 2.23s | 95.80ms | 136.80ms | **1238.88ms** | 0 |
| **`wal` (적용)** | **0.61s** | **0.11ms** | **0.27ms** | **0.41ms** | 0 |

### 측정 ② macOS arm64 (MacBook Air M2 8GB) · Python 3.14.7 · SQLite 3.53.4 — **개발·시연 환경**

| 저널 모드 | 쓰기 시간 | 읽기 평균 | p95 | **최대** | 잠금 오류 |
|---|---|---|---|---|---|
| `delete` (기존 기본값) | 0.48s | 3.44ms | 20.14ms | **22.71ms** | 0 |
| **`wal` (적용)** | **0.29s** | **0.19ms** | **0.34ms** | **1.51ms** | 0 |

읽기 표본 50회 / 45회. 이 표가 **시연 환경의 정본**이다(환경 ① 은 느린 저장장치 대조군).

### 읽는 법

**방향은 두 환경에서 같고, 크기만 다르다.**

| | 기본값 최대 지연 | WAL 최대 지연 | 쓰기 |
|---|---|---|---|
| macOS M2 (시연 환경) | 22.71ms | **1.51ms** | 1.7배 빨라짐 |
| Linux VM (느린 저장장치) | 1238.88ms | **0.41ms** | 3.7배 빨라짐 |

- **시연용 맥에서는 기본 모드로도 체감 문제가 없다.** 화면 폴링 간격이 3초인데 최악 지연이 22ms다.
  "SQLite 라서 느리다" 는 우리 환경에서 사실이 아니었고, 그걸 재보고 확인했다.
- **느린 저장장치에서는 최악값이 1.2초까지 벌어진다.** 학원 PC·저사양 노트북에서 시연할 때
  실제로 만날 수 있는 값이다. 환경이 바뀌면 문제가 되는 종류의 위험이다.
- WAL 은 두 환경 모두에서 최악 지연을 **1.5ms 이하**로 내렸고, 쓰기 처리량도 같이 올랐다.

그래서 WAL 적용 근거는 "지금 느려서" 가 아니라 **"비용이 0인데 최악값을 지운다"** 이다.
프라그마 한 줄이고, 스키마도 애플리케이션 코드도 안 바뀌며, 어느 환경에서도 나빠지지 않는다.
측정된 문제와 이론적 위험을 구분해서, **측정된 문제는 없었지만 위험은 제거했다** 가 정확한 서술이다.

적용 위치는 `store/sqlite.py` 의 `connect()` 한 곳이다(`auth_store` 도 같은 함수를 쓴다).
저장소마다 따로 열면 '어떤 연결은 WAL, 어떤 연결은 아님' 이 되어 보장이 반쪽이 된다.

## PostgreSQL 로 가야 하는 조건

아래 중 **하나라도** 생기면 옮긴다. 지금은 셋 다 해당하지 않는다.

1. **동시 진단을 허용할 때** — 잡 큐 워커를 2 이상으로 올리는 순간 다중 쓰기가 생긴다.
2. **다중 인스턴스로 배포할 때** — 프로세스가 여러 대면 파일 DB 를 공유할 수 없다.
3. **공격 시도 로그를 분석 대상으로 쓸 때** — `hit_assets` 를 JSONB 로 질의하거나
   기법별 집계를 상시 돌리기 시작하면 그때가 이관 시점이다.

## 이관 비용 (실측)

| 항목 | 수량 |
|---|---|
| `?` 파라미터 바인딩 → psycopg `%s` | 57개 |
| SQLite 전용 구문 (`INSERT OR REPLACE`, `AUTOINCREMENT`, `PRAGMA table_info`, `executescript`, `sqlite3.Row`) | 13곳 |
| `sqlite3` 를 직접 쓰는 파일 | 9개 (테스트 7개 포함) |
| 타입 변환 | `INTEGER(0/1)→BOOLEAN`, `TEXT(ISO8601)→TIMESTAMPTZ`, `TEXT(JSON)→JSONB` |
| 그 외 | 팀원 PC 전체에 PG 설치·계정, 테스트 격리 방식 재작성(파일 DB → 스키마 생성/삭제) |

DDL 은 이미 작성해 뒀고 **PostgreSQL 16 에서 실제로 실행 검증**했다 —
생성 8테이블 / 인덱스 19개, 재실행 멱등, `ON DELETE CASCADE` 및 JSONB 질의 동작 확인.
`tests/test_db_pragmas.py` 가 두 스키마의 테이블 집합이 어긋나지 않도록 강제한다.

## 결과

- 지적의 실질(동시성)은 해결됐고 수치가 남았다.
- 이관 경로가 문서가 아니라 **실행 검증된 DDL** 로 존재한다.
- 지금 옮기지 않는 이유가 "안 해봐서" 가 아니라 **조건이 아직 아니어서** 임이 기록됐다.
